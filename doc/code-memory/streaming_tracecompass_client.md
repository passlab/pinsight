Trace streaming demo (see [[project-overview]], doc/trace_streaming_design.md §12): client-side setup solved 2026-07-15.

**Tunnel topology:** laptop cannot ssh directly to a specific login node; `tuolumne.llnl.gov` load-balances. Tunnel with remote-side target: `ssh -S none -N -L 5344:tuolumne2152:5344 -L 2222:tuolumne2152:22 yan10@tuolumne.llnl.gov` (login→login internal TCP to :5344 verified open; relayd must bind `-L tcp://0.0.0.0:5344`). `-S none` avoids the user's ControlMaster mux, which refuses added forwards.

**Eclipse/TraceCompass SSH ("Algorithm negotiation fail") — root cause CONFIRMED 2026-07-16: the preference fix alone suffices** (verified on fresh Eclipse + stock JSch 0.1.55, ~/.p2 wiped):
1. THE fix: workspace prefs override JSch defaults with DH-only KEX (predates ECDH). Fix in `<workspace>/.metadata/.plugins/org.eclipse.core.runtime/.settings/org.eclipse.jsch.core.prefs`: prepend `ecdh-sha2-nistp256,ecdh-sha2-nistp384,ecdh-sha2-nistp521` to BOTH `CVSSSH2PreferencePage.PREF_KEX_METHODS` and `..._ORDER` (edit with Eclipse closed; the pref UI cannot express ECDH). Tuolumne sshd offers ONLY ecdh KEX, rsa-sha2/ecdsa host keys, sha2 MACs.
2. Optional-but-recommended: replace bundled `com.jcraft.jsch` 0.1.55 (2018) with maintained mwiede fork (Maven `com.github.mwiede:jsch`, 2.28.4 used): masquerade the jar as the old bundle by editing META-INF/MANIFEST.MF → `Bundle-SymbolicName: com.jcraft.jsch`, `Bundle-Version: 0.1.55.v20230916-1400`, Export-Package version likewise; copy over old jar keeping old filename (in `~/.p2/pool/plugins/` for Oomph installs, or `Eclipse.app/Contents/Eclipse/plugins/`); restart `-clean`. Fork gives detailed errors (`algorithmName=... jschProposal=... serverProposal=...`) — essential for diagnosis (stock gives bare message); also needed for rsa-sha2 host keys / RSA pubkey auth. `Implementation-Version` (not Bundle-Version) distinguishes fork from stock after masquerade. Full recipe: doc/trace_streaming_design.md §13.

**Why:** TraceCompass Fetch Remote Traces (SFTP, batch) and the Control view (needed to open live lttng sessions) both ride this JSch stack. Fetch confirmed working after the fix.

**Fourth gotcha (solved 2026-07-16): Control view's `Import...` greyed out for an already-running live session.** Known TraceCompass behavior (per Eclipse tracecompass-dev list, maintainer B. Hufmann): Import's enabled state can get stuck if the session was already `--live`/started via CLI *before* TraceCompass's Control view connected — the UI's cached state doesn't always pick up "already running." Fix: click `Refresh` on the session node (often enough); if not, Stop then Start the session *from within the Control view itself* (not CLI) — this reliably re-enables Import. Once enabled, Import should link the live trace into a "Remote" tracing project and auto-open it, updating continuously as events arrive (per docs; not yet confirmed the opened trace actually live-updates over the network — older mailing-list threads claimed a same-host relayd/TraceCompass requirement, current-version behavior TBD).

**Fifth gotcha (solved 2026-07-16): Fetch Remote Traces failed with `SAXParseException`/"error retrieving node configuration" caused by a second stale bundle — `org.apache.commons.compress` 1.4.1 (Eclipse Orbit, from 2013!) — needed the same masquerade-swap as JSch.** Root cause: TraceCompass's fetch wizard probes whether a remote path might be a tar archive via `TarArchiveInputStream.getNextEntry()`, a method signature only present in commons-compress ≥1.21 (the generified `ArchiveInputStream` API); the ancient 1.4.1 bundle throws `NoSuchMethodError`. Fix: same masquerade pattern as JSch — download latest from Maven Central (`org.apache.commons:commons-compress`), edit `META-INF/MANIFEST.MF` (`Bundle-SymbolicName: org.apache.commons.compress` — note the Maven jar's own name is `org.apache.commons.commons-compress`, must be trimmed; `Bundle-Version` and every `Export-Package` `version="..."` set to the old value, e.g. `1.4.1.v201301140946`), swap into the same `~/.p2/pool/plugins/` (Oomph-managed installs) or `Eclipse.app/Contents/Eclipse/plugins/`.

**Critical rebuild gotcha:** don't hand-edit-then-`zip -qr` naively — two failure modes hit in practice: (1) CRLF line endings in the original Bnd-generated manifest + a naive line-rewrap script that only `chomp`s `\n` (not `\r`) produces MIXED line endings; simplest fix is normalizing the whole file to plain `\n` first. (2) Using `zip` to patch/update a single file into an already-built jar can physically relocate `META-INF/MANIFEST.MF` deep into the archive (seen: entry 638 of 645) — several jar/OSGi loaders read jars as a sequential stream and require the manifest as the first (or one of the first) entries, so a buried manifest makes the bundle silently vanish from Eclipse's Plug-ins list entirely (not just show wrong content). **Always rebuild with `jar cfm <out.jar> META-INF/MANIFEST.MF -C <dir> .`** (real JDK `jar` tool, not raw `zip`) — guarantees manifest-first placement. Verify with `unzip -l <jar> | head -5` before installing.

**Also note the 72-byte MANIFEST.MF line-wrap rule: it's 72 content bytes, terminator is separate/additional** (confirmed against the actual JDK `Manifest.make72Safe()` source) — don't second-guess lines that are exactly 72 chars, those are correctly at the limit, not over it.

**macOS gotcha: `-clean` only takes effect via a real launch argument from Terminal** (`Eclipse.app/Contents/MacOS/eclipse -clean` or `open -n Eclipse.app --args -clean`) — quitting/reopening from the Dock/Finder does NOT pass it, silently leaving the OSGi bundle-state cache (which can retain info from a previously-broken bundle swap) untouched. This caused an apparently-still-broken bundle to persist even after the jar itself was fixed and hash-verified in place; a proper Terminal-launched `-clean` resolved it immediately.

**Sixth gotcha (UI-only, solved 2026-07-16): imported snapshot trace looked empty.** LTTng UST traces conventionally end in `.../uid/<uid>/64-bit`, so two different imported traces (e.g. an old batch trace + a new snapshot) end up as two tree nodes with the literal same name `64-bit`. Clicking a child view (e.g. `LTTng-UST CallStack`) under one trace can leave the Events editor showing whichever trace tab was already open, not the new one — looks like "no data" but isn't. **Fix: double-click the trace element itself** (not a child view) to force a fresh editor tab. Confirmed: real event data appeared once opened this way.

**Third gotcha (solved 2026-07-16): "Error retrieving node configuration" / SAXParseException "Content is not allowed in trailing section" when TraceCompass connects the Control view** — even after the SSH algorithm fix. Root cause: `~/.profile.linux` (LLNL's per-user copy of the CFEngine skel file) had an unguarded `trap "echo 'logout'" 0` — fires on every shell exit, no ENVIRONMENT check (unlike the tset/stty block just above it, which IS guarded). When Eclipse's remote-command execution sources this file (login-shell semantics), the trap appends a stray `logout` line after the command's real XML output → trailing content → XML parse failure. Fix: wrap the trap in `if [ "$ENVIRONMENT" = INTERACTIVE ]; then ... fi`, matching the existing guard pattern in the same file (`.profile` sets `ENVIRONMENT=BATCH` for any non-interactive/non-`-i` shell, which is what SSH-exec'd commands are). This is a user-owned file (`/g/g19/yan10/.profile.linux`, mode 600), safe to edit directly — not a shared system file.
